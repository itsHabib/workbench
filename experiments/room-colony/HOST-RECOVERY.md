# Lose the host, retain the work

The Linux host owns the mailbox, broker, launchers and Room state. Force-stopping
that host kills the broker and a live verifier Room. After boot, one explicit
`apply` starts fresh workers against the retained disk. The Mac only issues test
commands; no Mac service participates in their recovery.

This replay uses the two proposals generated by the earlier live model trial.
**No model credentials or new model calls are involved.** It tests recovery,
not independent cloud inference. The same Linux disk must survive.

## Observed result

[Published receipts](receipts/host-loss/): **14/14 recovery checks passed**.
Two workers finished after the host reboot; the original verifier's interrupted
attempt remains uncollected. Repeated apply kept live workers, then became a
no-op after completion. Current-boot Rooms were empty at shutdown.

Passage at `dc7124c8b574c5e3b9f1ad4948e34b3ce36f1821` accepted both handoffs and
rejected changed source. **33 offline tests pass.** Independent review found
three recovery defects; their fixes passed a focused re-review and this final
power-loss trial. Failed earlier attempts remain private rather than being
folded into the passing run.

## Lessons

- **A kernel boot ID is stronger than a missing PID.** Same-boot disappearance
  remains ambiguous; after reboot the old kernel's processes cannot survive.
- **Keep incomplete evidence incomplete.** The killed verifier has no terminal
  or collection receipt. Preserve its overlay/logs instead of inventing success.
- **Submission, completion and collection differ.** A done marker alone does not
  establish collected success. A replacement can finish that interrupted handoff.
- **Durability includes names.** Sync files and parent directory entries before
  starting workers. Atomic rename alone does not cover power loss.
- **Preparation is part of recovery.** Reinstall Rooms forwarding rules after a
  host reboot. Do not broaden guest access to private networks.
- **Small OS details matter.** Keep Firecracker socket paths under 108 bytes and
  SSH private keys mode 0600. Both caused real failed or delayed attempts here.

## Reproduce on a dedicated Linux Rooms host

Use an otherwise idle disposable host. Put this directory's Python files there,
plus saved model `1/` and `2/` directories containing `request.json` and `reply.json`
from a previous private colony run. The public candidate files are outputs, not
complete input/reply pairs. Keep the generated run directory private.

```sh
sudo python3 host.py init /opt/c-a \
  --rooms /path/to/rooms --image /path/to/agent.ext4 \
  --toolstore /path/to/python-toolstore --key /path/to/id_rooms \
  --replay /path/to/saved-model
sudo python3 host.py apply /opt/c-a
sudo python3 host.py plan /opt/c-a
```

Wait for `artifacts/review-1.json`, author exit 137, and a live verifier waiting
for proposal two. Record the current kernel boot ID, candidate-one digest and
plan in `before-power-loss.json` (the published receipt shows the shape). Then
force-stop the dedicated host from its hypervisor. This trial used
`limactl stop --force rooms-host`, which SIGKILLs the VM driver.

Restart the host, restore networking with Rooms' `scripts/setup-tap.sh --host`,
and confirm the boot ID changed while the candidate digest stayed the same.
Record `after-power-loss.json`, then:

```sh
sudo python3 host.py plan /opt/c-a
sudo python3 host.py apply /opt/c-a
# When both replacement workers finish:
sudo python3 host.py audit /opt/c-a
sudo python3 host.py apply /opt/c-a  # complete; starts no workers
sudo python3 host.py stop /opt/c-a
```

`stop` checks the current-boot Room inventory, stops the broker and retains all
evidence. Old-boot overlays remain for inspection; they are not running VMs.
Archive needed evidence before deleting this explicitly owned lab directory.
The HTTP listener binds the Linux host's interfaces with an ephemeral bearer
token; keep it behind the lab firewall. It is not a public multi-tenant service.

## Actual Passage handoff

Build `cmd/passage` from [PR #353](https://github.com/itsHabib/workbench/pull/353),
then use its CLI as an external artifact consumer:

```sh
python3 passage_check.py --binary /path/to/passage \
  --run /path/to/collected-host-run --out /new/path/to/passage-evidence
```

The adapter validates source/qualification binding and the recovery audit,
records two deterministic acceptance judgments, and advances verification →
recovery → complete. It then changes the qualified source: Passage must report
`ready: false` and require reopening verification. Restoring the exact source
restores readiness. This is actual Passage behavior, not a simulated JSON reply.

The caller supplies attribution. This does not establish independent review,
merge authority, fresh inference, disk-loss recovery or cross-host consensus.

## Fleet and Terraform next

The existing Terraform/GCP experiment already provisions a nested-KVM host.
This Linux runner can be staged there, but this trial used Lima. No new cloud
infrastructure was created. Fleet still needs a real Rooms provider/transport
adapter; wrapping this script in another `local-exec` would not supply live
reconciliation. The next test should move the retained disk to a different host
and let Fleet own worker launch/observation, keeping this recovery workload.
